第 0 步：装到 Codex

先确认装好了。已经装过就跳过这一节。

你在哪装
命令
全局（所有项目可用）
npx -y skills add ccwq/ccwq-skill-list --agent codex --skill project-self-memory -g
当前项目
npx -y skills add ccwq/ccwq-skill-list --agent codex --skill project-self-memory

装完确认一下。Codex 读的是 .agents/skills/ 目录:

ls .agents/skills/project-self-memory/          # 项目级
ls ~/.agents/skills/project-self-memory/         # 用户级
已验证 本机实测:--agent codex 把 skill 装到 .agents/skills/project-self-memory/(项目级)或 ~/.agents/skills/project-self-memory/(加 -g)。注意不是 .codex/skills/。

它替你做了什么

一句话:开工前读你过去攒的结论,收工时把新结论记下来。

原理 人的记性有两个毛病:忘了,和记错。这个 skill 对应两个机制。开工时把相关结论加载进 Codex 的上下文,解决忘了;收工时把结论写进项目里的记忆库,解决记错。记忆库跟着 git 走,团队共享;结论必须经过你确认,错的进不去。
时机
你看到什么
开工前
Codex 自动读相关记忆,把命中的结论放进上下文。你不用做任何事,通常也看不到提示。
干活中
Codex 用这些结论干活。想看它读到了什么,敲 $project-self-memory -l。
收工时
Codex 把新结论和评分暂存起来,不直接写进记忆库。
你要处理时
敲 $project-self-memory -c,Codex 逐条给你看,你决定哪条进库。
这一版最大的变化 收工时 Codex 不再直接写记忆库。它把结论先暂存在项目里的暂存区,跨会话保留。-c 时它逐条问你:写还是不写,写的话用什么措辞。这是本次更新的全部要点,第 3 节展开。

两个路径,别搞混

这个 skill 有两个目录概念。搞混了命令就跑不通。

路径
是什么
skill 目录
.agents/skills/project-self-memory/。代码在这里。这个路径是固定的,Codex 装的时候决定的。
记忆库目录
<项目根>/.project-self-memory/。你的记忆在这里。这个路径跟着项目走,会进 git。

所以调用 CLI 时,脚本路径用 skill 目录,操作对象用项目目录:

# 在项目根目录执行
node .agents/skills/project-self-memory/scripts/memory.mjs read
node .agents/skills/project-self-memory/scripts/memory.mjs cache list

# 或者显式指定要操作哪个项目
node .agents/skills/project-self-memory/scripts/memory.mjs \
  --project-root E:\my-project diagnose
坑 直接敲 node scripts/memory.mjs 在 Codex 下会失败——当前工作目录是项目根,不是 skill 目录。要么用上面的相对路径,要么用 skill 目录的绝对路径。

第 1 步：初始化

新项目第一次用,先建记忆库。在项目根目录执行:

node .agents/skills/project-self-memory/scripts/memory.mjs init
你会看到

PSM_INITIALIZED

项目下出现 .project-self-memory/ 目录,含 config.yaml 与空的 memory.md。同时项目根的 .gitignore 被写入忽略规则,暂存区与锁文件不会进版本库。查看器也部署好了。

确认库是好的:

node .agents/skills/project-self-memory/scripts/memory.mjs validate
你会看到

PSM_VALID

注意 初始化只在记忆缺失时做。已有库不要重跑,否则会丢掉已有记忆。validate 报错误时停止写操作,先修库。

第 2 步：干活,什么都不用敲

这是最常见的场景。正常提需求就行,记忆功能自动生效。

场景：修一个线上偶发超时的问题
你在 Codex 里输入

排查一下回源接口为什么偶发超时。

Codex 做的事

开工前静默加载相关记忆。它读到你上次留下的「回源接口在高峰期需要限流」,于是从限流方向查起,而不是从零开始。

Codex 做的事

收工时发现新结论:「回源接口在高峰期需要限流并加熔断」。这是全新、已验证、无冲突的结论,自动暂存到暂存区。

Codex 回你

「已暂存一条候选:回源接口在高峰期需要限流并加熔断。记忆库暂未改动,需要入库时敲 $project-self-memory -c。」

此刻的状态

暂存区多了一条候选。记忆库还是原样。措辞被改写过也没关系——暂存的正文已经是可直接入库的单行形态。

想看 Codex 读到了什么:

$project-self-memory -l

或者直接让它列出来:$project-self-memory 把相关记忆列出来。

为什么这样设计 旧版本 Codex 会直接把你没看过的结论写进记忆库。低价值或措辞不佳的结论从此混在记忆里,越积越多。现在你有机会在入库前改写它,或者干脆不要它。

第 3 步：处理候选（-c）

这是新流程的核心。-c 是候选进记忆库的唯一入口。

$project-self-memory -c
场景：攒了两三次任务的候选,现在一次性处理
你在 Codex 里输入

$project-self-memory -c

Codex 做的事

先跑 cache list 读暂存区,按目标记录分组。同一记录的矛盾候选聚成一组(既有加分又有扣分、或者有两条不同修改),独立新增每条一组。

Codex 问你

第 1 问／预计约 2 问。附上这一组的原文对照和选项。

你会看到每组的选项。选项按风险分档,这是有意为之:

候选类型
你看到什么
修改已有记忆
原文和新文案的对照。选项:改写后写入 / 丢弃 / 暂缓。注意没有「直接写入」。
新增、删除、加分、扣分
选项:写入 / 丢弃 / 暂缓。
目标已变的候选
选项:丢弃 / 基于现状重新评估。
为什么修改类没有「直接写入」 修改会覆盖一条已经存在的记忆正文。如果 Codex 暂存时看到的是旧版本,而你后来手工改过这条记忆,直接写入就等于用旧判断覆盖你的新判断。所以修改类必须你看一眼、确认一次。改写后的措辞由你在选项里给。
继续
你在 Codex 里输入

选「改写后写入」,措辞改成「回源接口在高峰期需限流并加熔断」。

Codex 做的事

只处理这一条。跑 cache apply --id <id> --decision write --content-file <改写后的正文>。落库走既有写入栈:加锁、备份、乐观并发检查、单行契约校验。

Codex 回你

「[0001][事实] 回源接口在高峰期需限流并加熔断」——落库后回读这条记录,把结果给你看。

此刻的状态

这条候选状态变成已入库。暂存区保留这条记录作为痕迹,不再出现在待处理列表里。

几个边界行为:

情况
Codex 的行为
暂存区是空的
直接告诉你没有待处理。不编问题,不请求空授权。
你中途打断
已处理的已经落库生效,未处理的留在暂存区,下次继续。
某一条失败
这一条失败不影响其他条。失败的那条保持待处理,你可以重试。
你选「暂缓」
不动它,也不标记处理。留在暂存区等你下次。
选择即授权 你选「写入」本身就是对这一条的写入授权,Codex 不会再问一遍「确定要写吗」。但选「暂缓」或没选,都不算授权。

手动核对暂存区

想在 Codex 之外看候选,直接敲 CLI:

# 看有哪些候选、分了几组
node .agents/skills/project-self-memory/scripts/memory.mjs cache list

# 看单条的原文对照
node .agents/skills/project-self-memory/scripts/memory.mjs cache show <event_id>

# 清掉已处理和已失效的条目
node .agents/skills/project-self-memory/scripts/memory.mjs cache prune --older-than 7d

候选失效了怎么办

暂存之后,你或别人改了目标记录。这时旧候选的判断依据已经不成立。

场景：你昨天让 Codex 暂存了一条修改建议,今天你手工改了同一条记录
你在 Codex 里输入

$project-self-memory -c

Codex 做的事

这组被标成失效,单独成组展示:「目标已变更」。给你看暂存时的原基准和你现在的正文。

Codex 问你

选项只有两个:丢弃 / 基于现状重新评估。没有「直接写入」。

Codex 做的事

如果你坚持直接写,系统拒绝:PSM_CONFLICT: 目标记录已变更;请基于现状重新评估。这条候选保持待处理。

此刻的状态

失效候选不会被静默跳过。它照样出现在列表里、照样等你处理。你攒过的判断不会因为过期就消失。

原理 暂存时 Codex 记下了目标记录的版本指纹。读的时候比对一次,指纹不一致就是失效。这是同一套乐观并发机制在暂存层的镜像:不猜,只比对。

其他三个策展入口

这三个不处理暂存区,只扫记忆库本身。

你在 Codex 里输入
Codex 干什么
$project-self-memory -g 鉴权迁移
或「盘点一下这次有哪些经验值得沉淀」
扫描记忆库,找出新增、修订、合并、冲突和迁移候选,逐个问你。
$project-self-memory -r
或「评价一下」
只讨论本次会话实际用过且有结果的记录,给出加分、扣分或不评分的建议。
$project-self-memory -t 鉴权
或「清理一下」
只处理长期没帮上忙的记录,你可以保留、修订、停用或删除。
组合
说明
$project-self-memory -g -r
盘点与评分一起做,共享同一个问题编号和预计总数。切换不重置进度。-r -g 等价。
职责正交 -g、-r、-t 都不读暂存区。暂存区只由 -c 消费。旧的策展工作流完全不受这次改动影响。

评分与清理的实际命令

讨论到需要落盘时,Codex 会跑这些:

# 评分:vote 只接受 +1 或 -1
node .agents/skills/project-self-memory/scripts/memory.mjs score 0001 +1
node .agents/skills/project-self-memory/scripts/memory.mjs score 0001 -1

# 清零与修复
node .agents/skills/project-self-memory/scripts/memory.mjs score-reset 0001
node .agents/skills/project-self-memory/scripts/memory.mjs score-repair 0001 --positive 3 --negative 0

# 状态:active / review / disabled
node .agents/skills/project-self-memory/scripts/memory.mjs status 0001 review
原理 评分不是计数器。分值来自一张只追加的账本,每次写库时按账本重算成 memory.md 里的数字。好处是每次评分都留痕,出问题能追溯;坏处是正文一改,旧评分自动作废——这是对的,因为那条经验可能已经被改了。

一条底线证据不足的记忆只标「未证实」并保留,不会因为旧、无关或暂未核验就被删。

直接改一条记忆

直接改不需要经过暂存区,也不需要 -c。直接对 Codex 说就行。

场景：一条决策变了
你在 Codex 里输入

「回源接口在高峰期需要限流」这条已经不成立了,改成「回源接口需要限流并加熔断与降级」。

Codex 做的事

先看这条的现状和它的评分历史,把改写后的正文给你确认。

Codex 做的事

你确认后写入,并说明一个副作用:正文变了,版本就变了,这条之前的评分不再适用,正负分清零。

此刻的状态

记忆已更新。想保留原来的评分,明说「保留评分」,Codex 会记一条修复事件留痕。

其他直接操作的说法:

你说
结果
「这条删掉」
记录删除。编号永不复用。
「这条先停用」
状态改为停用。不再出现在读取结果里,也不进检索。保留内容,随时能恢复。
「这条标记为待复核」
状态改为待复核。同样不再出现在读取结果里。
「把 0001 和 0002 合成一条」
合并。保留较早的编号,删除另一个,合并谱系写进账本。
「这是长期决策」
写入时用决策类型。决策和约束不随时间衰减,事实会衰减,经验和避坑衰减更慢。

开关:自动还是手动

你可以决定哪些行为自动发生、哪些由你点头。

开关
关掉之后
自动读
Codex 不加载任何记忆。上下文里不会有记忆内容,连提示都没有。
自动存
收工时不暂存候选。记忆库和暂存区都不动。
自动评分
收工时不暂存投票候选。

有三种粒度:

粒度
怎么设
本次任务
在这次请求里说「这次不读记忆」「这次不要保存」。或用 $project-self-memory --no-load、--no-save、--no-rate。
本次会话
说「整个会话都不要读记忆」。或用 --no-load-session、--no-save-session、--no-rate-session。直到你恢复为止。
整个项目
改 .project-self-memory/config.yaml 里的 auto_load、auto_save、auto_rate。默认三个都开。
优先级 任务级覆盖会话级覆盖,会话级覆盖配置文件,配置文件覆盖默认值。粒度越近,优先级越高。这让你可以在一次特殊任务里临时关掉自动,而不必改项目配置。

改配置用 CLI,不要手改 YAML:

node .agents/skills/project-self-memory/scripts/memory.mjs config show
node .agents/skills/project-self-memory/scripts/memory.mjs config set auto_save false
node .agents/skills/project-self-memory/scripts/memory.mjs config validate

人工浏览:查看器

想用眼睛看整个记忆库,起一个本机网页。在项目根目录执行:

node .project-self-memory/view-memoery.js
你会看到

PSM_VIEWER_URL: http://127.0.0.1:<port>/#token=<hex>

浏览器自动打开这个地址。只监听 127.0.0.1,令牌只在进程与页面内存中,不落盘。

查看器能做
说明
浏览、改正文
正文、类型、状态可编辑。写入走与 CLI 相同的锁、备份、原子替换和乐观并发。
按标签筛选
多选任一匹配,按首标签分组。标签只读。
不能做
不碰暂存区。查看器只编辑记忆库记录。

无头环境加 --no-open:node .project-self-memory/view-memoery.js --no-open。

它不会替你做的事

它不做
为什么
自动把结论写进记忆库
这是这一版改掉的。结论先暂存,你确认后才进库。
自动删记录、合并记录
这两类操作不可逆。自动流程只暂存这类候选,落库必须经你确认。
自动改分类标准
分类标准是项目的公共约定,改动要具体授权。
把高分当真相
历史高分只说明过去奏效。当前状态仍要现场验证。
记录凭据、个人数据
记忆库跟着 git 走,进了版本库就等于公开。
按标签给记忆排序
标签只用于筛选和观察,不改变检索排名。

五个常见坑

坑 1：以为收工就写进去了
症状

Codex 说「已记录」,你过几天看记忆库却找不到。因为它只暂存了。

怎么办

敲 $project-self-memory -c。或者下次开工前先问「暂存区里有什么」。

坑 2：暂存区越积越多
症状

候选攒到几十条,处理时一轮问不完。

怎么办

待处理超过 20 条时 Codex 会提醒你。攒多了就分批处理,或者明确丢弃不需要的。已处理的和已失效的条目可以 cache prune 清理掉,但待处理的永不自动过期——攒多久都不丢。

坑 3：改了正文,评分归零
症状

你改了一条记忆,之前攒的正分没了。

怎么办

这是设计行为,不是 bug。评分绑定记录版本,正文变了旧评分就不适用。想保留就说「保留评分」。

坑 4：正文写多行被拒
症状

写入报 PSM_CONTRACT:正文必须是单行。

怎么办

一条记录写一件事,压成一行。不能用标题、列表、代码围栏开头。历史多行记录照常能读,只是新写的不行。

坑 5：以为「确认后保存」等于授权
症状

你说「可以,保存吧」,Codex 还是没写。

怎么办

「认可结论」「确认后保存」只是同意讨论结论,不是授权写操作。要授权就直接说「写入」「删掉」「改成……」。
