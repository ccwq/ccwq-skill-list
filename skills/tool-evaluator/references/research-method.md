# 调查方法

在候选通过 Gate 后读取。先宽后深地取证，并使每项关键结论的证据等级与时间范围可追溯。

## 六、采用漏斗式调查

不得一开始就对所有工具进行同等深度调查。

依次执行：

候选发现
→ Gate
→ 快速初筛
→ 标准调查
→ Top N 深度调查
→ 风险与敏感性分析
→ 必要时提出 POC

默认：

* 初始候选：按任务合理控制；
* 标准调查：聚焦通过 Gate 的候选；
* 深度调查：默认保留 Top 3；
* 最终重点推荐：通常 1–3 个。

如果候选很少，可跳过不必要阶段。

---


## 八、项目健康度必须单独分析

对于开源项目、开发工具和生态型工具，至少考虑：

* 项目年龄
* 最近活动
* Commit 活跃度
* Release 节奏
* Release 稳定程度
* Issue 首次响应速度
* Issue 解决速度
* Open Issue 趋势
* Bug 与 Feature Request 构成
* PR 响应速度
* PR 合并情况
* Contributor 数量
* 活跃 Contributor 数量
* 核心 Maintainer 数量
* Bus Factor
* 维护者集中度
* 社区讨论活跃度
* 社区讨论质量
* 文档更新
* Roadmap
* Breaking Changes
* 安全 Issue 响应
* 最近 30 / 90 / 365 天趋势
* 长期活跃趋势

Star、Fork、下载量等只能作为辅助信号。

对于每项关键健康度指标，使用：

指标值
→ 趋势
→ 上下文
→ 解释
→ 风险判断

例如：

“最近半年仅发布一次”

不能直接判定负面。

需要判断：

* 是否已经成熟稳定；
* 是否仍在维护；
* 是否存在长期未修 Bug；
* Commit 是否仍持续；
* 是否正在开发下一大版本。

## 九、区分证据等级

对重要结论标记证据等级。

## L1：声明证据

包括：

* 官网
* 官方文档
* README
* 官方 Feature List

只能证明：

“官方声称支持”。

## L2：行为证据

包括：

* Source Code
* Commit
* Release
* Issue
* PR
* Discussion
* Maintainer 回复
* 可靠用户报告

可以证明实际项目行为与已知问题。

## L3：实测证据

在目标环境完成实际验证。

只有 L3 才允许使用：

* 已验证
* 实测可用
* 实测不兼容
* 实测失败

未经 L3 验证，不得把 L1/L2 描述为“实测”。

如不同证据冲突：

L3 > L2 > L1

但必须同时说明冲突情况。

---

## 十、处理时间维度

优先分析近期状态，同时保留长期趋势。

建议窗口：

* 30 天：短期变化
* 90 天：近期活跃
* 12 个月：主要趋势
* 更长历史：判断长期稳定性

不要因为一个短期异常直接推翻长期趋势。

也不要因为历史辉煌忽略当前已经衰退。
