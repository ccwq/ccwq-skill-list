# 报告与 POC

在形成决策报告或考虑实测时读取。POC 用于验证可能改变推荐的关键假设，并始终受明确授权约束。

## 十六、POC / 实测策略

资料调查完成后，只对 Top N 候选考虑实测。

POC 不追求完整测试全部功能，而是验证：

“最可能改变最终推荐的关键假设”。

例如：

* Windows 自动化是否可靠；
* 自定义 API 是否真正兼容；
* 数据是否可迁移；
* CLI 是否支持无人值守；
* 某关键集成是否真实可用。

POC 前必须：

1. 列出待验证假设；
2. 说明验证方法；
3. 说明环境影响；
4. 说明可能修改的对象；
5. 说明风险；
6. 说明回滚方式；
7. 获得用户明确授权。

未授权时只生成测试方案，不执行实际操作。

---


## 十八、最终报告结构

最终输出必须优先帮助用户“做决定”，而不是堆砌调查资料。

按以下结构输出。

## 1. 结论摘要

说明：

* 推荐首选
* 推荐理由
* 次选
* 不同场景下的条件性首选
* 明确不推荐的候选

## 2. 用户需求与 Gate

列出：

* 核心目标
* 硬性需求
* 动态 Gate
* 主要偏好
* 关键环境约束

## 3. 候选池

说明：

* 初始候选
* 候选来源
* 淘汰工具
* 淘汰原因

## 4. 核心对比表

至少包含：

* 工具
* 核心能力
* 场景适配
* 项目健康
* 稳定性
* 安全
* 生态
* 成本
* 长期风险
* 原始分
* 加权分
* 置信度

根据工具类型动态增加字段。

## 5. Top 候选深度分析

对每个候选分别说明：

* 最强优势
* 最大缺陷
* 最适合谁
* 不适合谁
* 项目健康
* 社区维护
* 关键 Issue / 风险
* 长期风险
* 证据等级
* 未验证项

## 6. 社区与项目健康分析

特别比较：

* Release
* Commit
* Issue
* PR
* Maintainer
* Contributor
* 社区
* Breaking Changes
* 最近趋势

不得只列数字，必须解释含义。

## 7. 权重与评分

展示：

* 本次权重
* 权重为什么这样设置
* 原始分
* 加权分

## 8. 敏感性分析

说明：

* 哪些权重变化会改变排名；
* 推荐是否稳定；
* 哪些工具实际属于同一梯队。

## 9. 风险与未知项

分成：

* 已确认风险
* 潜在风险
* 关键未知项
* 是否可能推翻结论

## 10. POC 建议

若需要：

列出 Top N 最值得验证的关键假设。

未经用户授权，不执行。

## 11. 最终决策

使用：

* 首选
* 次选
* 条件性首选
* 不推荐

并分别说明：

“为什么”。

最后补充：

“出现什么条件变化时，我会改变当前推荐。”

---

## 十九、输出质量要求

结论必须：

* 可追溯；
* 可验证；
* 可解释；
* 可复现；
* 明确区分事实与推断；
* 明确区分声明与实测；
* 明确表达不确定性；
* 关注用户实际用途；
* 避免营销语言；
* 避免简单罗列 Feature；
* 避免无意义的信息堆砌。

调查过程中如发现：

* 用户前提错误；
* 工具已经更名；
* 项目已经停止；
* 功能已经发生重大变化；
* 原候选其实不是同类产品；

应暂停原比较逻辑，先说明问题并重新建立正确比较基线。
