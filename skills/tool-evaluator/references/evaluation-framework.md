# 评价框架

在比较通过 Gate 的候选时读取。评分是解释工具，不是掩盖不确定性或制造虚假精确度的结论机器。

## 七、通用评价维度

根据任务动态选择，不要求机械覆盖所有维度。

重点考虑：

## 产品与功能

* 核心功能完整度
* 功能深度
* 功能广度
* 差异化能力
* 可扩展性
* API 能力
* CLI 能力
* 自动化能力
* 集成能力
* 配置灵活度

## 使用体验

* 安装难度
* 初始配置成本
* 学习曲线
* 日常操作复杂度
* 文档质量
* 错误信息质量
* Debug 能力
* 可观测性

## 稳定性与工程质量

* 稳定性
* 性能
* 资源占用
* API 稳定性
* Breaking Changes
* 向后兼容
* 测试覆盖情况
* 发布质量
* Bug 密度迹象

## 兼容性

* 操作系统
* 架构
* Runtime
* Shell
* 浏览器
* IDE
* API
* 协议
* 现有技术栈
* 第三方服务

## 安全与隐私

* 安全设计
* 安全事件历史
* 漏洞响应
* 权限模型
* Secret 管理
* 数据存储位置
* 遥测
* 数据外传
* 本地化能力

## 成本

同时考虑：

* 购买成本
* API 成本
* 基础设施成本
* 运维成本
* 学习成本
* 迁移成本
* 时间成本
* 隐性成本

## 长期使用风险

* 供应商锁定
* 数据锁定
* 格式开放性
* 配置可迁移性
* 项目持续性
* 商业模式风险
* License 风险
* 生态依赖风险

## 十一、评分模型

使用“原始评分 + 动态权重”的混合模型。

默认每个维度：

0–10 分。

必须同时保留：

* 原始分
* 当前权重
* 加权分
* 评分依据

权重来源分三层。

## 11.1 基础权重

不可被完全忽略，例如：

* 核心能力
* 稳定性
* 安全性
* 项目健康
* 长期可维护性

## 11.2 场景动态权重

根据当前任务自动调整。

例如个人 CLI：

提高：

* 自动化
* 安装维护成本
* CLI 体验
* 跨平台

企业平台：

提高：

* 权限
* 审计
* SLA
* 治理
* 长期支持
* 数据迁移

## 11.3 用户覆盖

用户明确表达的偏好具有最高优先级。

用户的“必须”需求优先转换为 Gate。

“偏好”则转换为权重调整。

---

## 十二、不得制造虚假的精确度

例如：

A = 87
B = 86

不能简单得出：

“A 明显优于 B”。

需要判断：

* 分差是否显著；
* 证据质量是否相近；
* 权重稍微变化是否会逆转；
* 是否存在未验证关键变量。

必要时将工具划分为：

* 第一梯队
* 第二梯队
* 不推荐

---

## 十三、进行权重敏感性分析

对于最终 Top 候选，检查：

如果关键权重在合理范围内变化：

* 排名是否稳定？
* 首选是否改变？
* 哪个权重最容易改变推荐？

根据结果标记：

* 稳健推荐
* 条件性推荐
* 高度依赖偏好

示例：

“如果将生态权重由 10% 提高到 20%，B 会超过 A，因此 A 并非绝对优势，推荐主要取决于你更重视功能还是生态。”

---

## 十四、证据置信度

最终每个重要结论标记：

* 高
* 中
* 低

置信度取决于：

* 证据来源质量
* 是否存在交叉验证
* 数据是否足够新
* 是否存在证据冲突
* 是否存在关键未知项
* 是否已经实测

工具得分与结论置信度必须分开。

高分工具可以是低置信度推荐。

---

## 十五、识别未知项

明确列出：

* 尚未确认的信息；
* 无法获得的数据；
* 相互冲突的证据；
* 可能改变最终推荐的未知因素。

将未知项分成：

* 不影响结论
* 可能影响结论
* 足以推翻结论

优先进一步调查第三类。

---


## 二十、默认参数

除非用户另行指定：

* 评分范围：0–10
* 深度候选：Top 3
* 主要趋势窗口：12 个月
* 近期窗口：90 天
* 短期变化窗口：30 天
* 证据优先级：L3 > L2 > L1
* 输出语言：跟随用户
* 调查优先使用最新可靠资料
* 核心结论尽量进行多源交叉验证

整个流程始终遵循：

发现候选
→ 建立 Gate
→ 快速淘汰
→ 标准调查
→ Top N 深挖
→ 动态评分
→ 风险分析
→ 敏感性分析
→ 必要时 POC
→ 决策报告

最终衡量标准不是：

“哪个工具分数最高？”

而是：

“基于当前用户的真实需求、环境、约束、长期风险和可验证证据，哪个工具最值得选择，以及为什么。”
