# 决策基线

在定锚和 Gate-first 阶段读取。将用户目标与硬约束转化为候选资格，不把致命缺陷稀释进总分。

## 一、核心原则

遵循以下优先级：

用户硬性需求 > 可验证事实 > 安全与兼容性 > 场景适配 > 长期可维护性 > 功能丰富度 > 流行度

禁止：

* 仅凭 Star、下载量、搜索排名判断工具优劣。
* 将高更新频率直接解释为维护更好。
* 将低更新频率直接解释为项目停滞。
* 将官方宣称的能力写成“已经验证”。
* 用综合总分掩盖致命缺陷。
* 对不同类型工具机械套用完全相同的指标。
* 为了制造明确排名而夸大微小分差。
* 对缺乏证据的指标自行编造数据。
* 未经授权安装、运行、修改配置、注册账号或执行 POC。

如结论存在明显不确定性，应明确表达，而不是强行选出赢家。

---

## 二、首先识别任务模式

根据用户输入自动选择：

### 模式 A：指定候选比较

适用于用户已经给出 A、B、C 等候选工具。

要求：

* 以用户指定工具为主体。
* 可以指出存在明显遗漏的替代方案。
* 未经必要性论证，不擅自无限扩大候选范围。

### 模式 B：探索筛选

适用于用户只描述需求，希望寻找合适工具。

通过多个来源构建候选池，包括：

* 官方项目与官网；
* GitHub / GitLab 等代码平台；
* 官方文档；
* 同类项目引用；
* Awesome / curated list；
* 技术社区；
* Issue / Discussion；
* 可靠的同类工具比较资料。

不得仅依赖“Top 10”“Best X”类聚合文章。

候选发现满足以下任一条件即可停止扩张：

* 已覆盖主要技术路线；
* 已获得足够数量的高质量候选；
* 连续新增候选没有带来明显能力提升；
* 新候选主要属于低质量长尾；
* 继续搜索的边际信息增益已经很低。

## 三、识别工具类别

先判断每个工具属于哪些类型，例如：

* CLI
* 桌面软件
* IDE / 编辑器插件
* 开发库
* SDK
* 框架
* AI Agent
* AI 编程工具
* 自托管服务
* SaaS
* 基础设施工具
* 自动化工具
* 数据库
* DevOps 工具
* 浏览器工具
* API 服务

允许多标签。

根据类别启用对应专项评价指标。

---

## 四、明确用户真实需求

从用户输入中提取：

* 核心用途
* 必须具备的能力
* 希望具备的能力
* 明确不能接受的条件
* 操作系统与运行环境
* 部署方式
* 是否要求开源
* 是否要求自托管
* 自动化需求
* API / CLI 需求
* 数据隐私要求
* 安全要求
* 预算
* 学习成本容忍度
* 运维成本容忍度
* 长期使用需求
* 迁移与锁定风险偏好
* 生态兼容要求

可以通过公开资料、文件、工具或环境确认的事实自行查证。

只有真正涉及用户偏好、目标和取舍，而且会改变推荐结果时，才向用户询问。

## 五、建立 Gate：先淘汰，再评分

所有候选必须先经过资格审查。

Gate 分为三层：

## 5.1 通用 Gate

检查：

* 核心需求是否缺失；
* 是否无法在目标环境运行；
* 是否已明显停止维护；
* 是否存在不可接受的安全风险；
* 工具是否实际可获取；
* 授权协议是否与用途冲突；
* 是否存在无法接受的数据或隐私问题。

## 5.2 类型专项 Gate

根据工具类型生成。

例如 CLI 可检查：

* 是否支持目标 OS；
* 是否支持非交互执行；
* 是否适合自动化；
* 是否支持目标 Shell / Runtime。

自托管服务可检查：

* 是否具备可靠部署方式；
* 数据是否能够备份；
* 是否能够迁移；
* 依赖复杂度是否可接受。

AI 工具可检查：

* 是否支持目标模型；
* 是否支持所需接口；
* Agent / Tool Calling 能力；
* 上下文限制；
* 自动化或无人值守能力。

## 5.3 动态 Gate

根据本次用户需求自动推导。

例如用户明确要求：

“必须开源、自托管、Windows 可运行”

则这些条件直接成为 Gate，而不是普通加分项。

---

Gate 结果必须分为：

* 硬淘汰
* 严重扣分
* 普通评分项

硬淘汰工具原则上不再参与最终综合排名，但必须保留淘汰原因。
