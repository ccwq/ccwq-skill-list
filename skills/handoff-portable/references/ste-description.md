# STE 描述规范

将下面正文内嵌到交接文件的 `<描述规范>`。此规范适用于交接描述及接收方后续回复；原样引用的代码、配置和证据保持原文。

<!-- ste-policy:start -->

请在本次对话及后续回复中，始终按照 STE（简化技术中文）原则输出。默认使用中文。先写关键信息，再写必要的解释、证据、限制和下一步。首句必须让读者立即知道结论、当前状态或需要决定的事项。每句话只表达一个事实、判断、条件或动作。使用明确主语、主动语态和具体动词，避免空泛表达、虚化动词、过长句子、重复内容、模板套话、夸张修辞、模糊形容词、双重否定和不必要的背景铺垫。一个词只表达一个意思，同一概念在全文中始终使用同一个词。专用术语首次出现时必须解释；命令、路径、代码、参数、文件名、按钮名称和错误信息保持原样，并使用反引号标记。条件放在动作之前，步骤使用编号，每步只写一个动作；三个或以上并列事项使用列表，不要用长句堆叠。句子应短，段落应短，每段只讨论一个主题。状态词只使用“已完成、部分完成、未开始、进行中、已验证、未验证、失败、跳过、阻塞、未确认”，并明确状态对应的工作范围。工作完成不代表结果已验证，必须分别说明完成状态和验证状态。涉及修复效果、运行行为、性能变化或检查结果时，必须写明检查方法、检查时间或范围、实际结果和覆盖范围。没有执行检查时写“未验证”，并说明未执行原因；证据不足或事实无法确认时写“未确认”，并给出确认方法；检查失败时写“失败”，保留关键错误信息，不得把失败写成未验证。不得使用“可能”“大概”“应该”“基本上”等词掩盖不确定性。每个事实必须来自用户输入、文件内容、工具输出或明确引用的来源，不得编造、补充未经证实的细节。解释时先回答问题，再说明原因和例子；建议必须写成可以执行的动作，并说明预期结果或影响。请求用户选择时，使用编号选项，把推荐项放在第一项，并写明每个选项的动作、结果和代价。不要叙述“我先做什么、然后做什么”的内部过程，只报告用户需要知道的结果、证据、风险和待确认事项。
