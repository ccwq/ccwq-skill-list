# Spec: view-memoery 管理 cache（查看 / 编辑并入 / 丢弃 / 清理）

## Problem Statement

PSM 的 cache 暂存区（`.project-self-memory/cache.jsonl`）目前只有一条处理通路：CLI `cache list` / `cache show` 加 `-c/--cache-write` 选择题流程。人工想看「这阵子自动攒下了哪些候选」、想顺手修订一条措辞再入库、想丢掉明显的垃圾候选，都必须开着终端让 agent 跑 CLI 逐条问答。

同时，`init` 会把自包含单文件查看器 `view-memoery.js` 部署到每个项目，它已经是人工改正文/类型/状态的第二写入口，但完全不感知 cache：用户在查看器里看不到候选积压，更谈不上处理。

psm-cache 规格曾倾向「首版查看器不碰 cache」。现在用户明确开这张卡：查看器要能管理 cache——查看、编辑后并入（落库）、丢弃、清理。

## Solution

从用户视角：启动查看器后，工具栏出现「暂存区」入口，展示 cache 里全部待处理候选，按目标记录分组，失效候选单独标注。每条候选可以：

- **查看**：操作类型、目标 refid、候选正文、证据（理由/观察/来源/暂存时间）、失效对照（原基准 vs 现状）。
- **编辑并入**：正文可改写后写入（对应 `-c` 的「改写后写入」）；新增/修订候选落库后条目转已处理，列表即时刷新。
- **丢弃**：不落库，条目转已丢弃。
- **清理**：一键清掉全部已处理与已失效条目（对应 `cache prune`）。

查看器与 CLI 共用同一套写入语义与安全模型：锁、备份、乐观并发、单行契约、失效拒直写。没有 CLI 时查看器独立可用；两边同时操作时互不破坏。

## User Stories

1. 作为 PSM 用户，我希望在查看器里看到暂存区的全部待处理候选，以便不用开终端就知道积压了什么。
2. 作为 PSM 用户，我希望候选按目标记录分组展示，以便同一条记录的多个候选一起判断。
3. 作为 PSM 用户，我希望每条候选能看到操作类型（新增/修订/删除/调分）、目标 refid 与候选正文，以便知道它想做什么。
4. 作为 PSM 用户，我希望修订类候选展示原正文与新正文对照，以便判断改动是否必要。
5. 作为 PSM 用户，我希望候选展示内联证据（理由、观察、来源、时间），以便判断这条结论是否可信。
6. 作为 PSM 用户，我希望在查看器里改写候选正文后并入记忆库，以便修正措辞而不用回终端跑 `-c`。
7. 作为 PSM 用户，我希望新增/修订候选可以原样直接写入，以便无需逐条改写。
8. 作为 PSM 用户，我希望在查看器里丢弃候选，以便垃圾候选不进记忆库。
9. 作为 PSM 用户，我希望删除与调分候选在写入前有确认，以便高风险操作不被误触。
10. 作为 PSM 用户，我希望失效候选（目标记录已被改/删）被单独标注并展示「原基准 vs 现状」，以便不误把过时判断写进库。
11. 作为 PSM 用户，我希望失效候选不能直接写入，以便与 `-c` 的失效语义一致。
12. 作为 PSM 用户，我希望一键清理已处理与已失效条目，以便暂存区不无限膨胀。
13. 作为 PSM 用户，我希望写入成功后立即看到落库结果与刷新后的列表，以便确认操作生效。
14. 作为 PSM 用户，我希望候选写入后条目转为已处理而不是消失，以便保留审计痕。
15. 作为 PSM 用户，我希望操作失败（冲突/锁忙/契约不过）时草稿保留并说明原因，以便重试不丢内容。
16. 作为 PSM 用户，我希望外部（CLI 或另一进程）改动后查看器提示冲突而不是静默覆盖，以便并发安全。
17. 作为 PSM 用户，我希望暂存区为空时查看器直接说明没有待处理项，以便不被空操作困惑。
18. 作为 PSM 用户，我希望查看器不提供「新建候选」，以便暂存入口仍然只有 `-a` 与自动收尾，职责不扩散。
19. 作为 PSM 用户，我希望 pending 候选在查看器里永不自动过期，以便攒多久都不丢。
20. 作为维护者，我希望查看器复用 cache 既有读写原语与状态机，以便不出现第二套 cache 语义。
21. 作为维护者，我希望查看器写入走与记录编辑相同的锁、备份、原子替换与全量校验栈，以便不引入第二套并发模型。
22. 作为维护者，我希望调分候选落库复用账本幂等键（`cache-apply-<event_id>`），以便重试不重复计分。
23. 作为维护者，我希望单文件构建产物自动包含 cache 模块，以便产物与源码不分叉。
24. 作为维护者，我希望查看器 HTTP 契约文档与实现同步，以便宿主接入有依据。
25. 作为维护者，我希望行为有 CLI 黑盒测试覆盖（走部署产物 + HTTP），以便回归可发现。
26. 作为维护者，我希望查看器 cache 操作受与记录编辑相同的令牌/Origin/Host/限长安检约束，以便不扩大攻击面。
27. 作为维护者，我希望 `store_revision` 口径不变（仍只哈希 memory.md 与 evidence.jsonl），以便 cache-only 变更不打断用户的记录编辑流。
28. 作为维护者，我希望 CLI 行为零改动，以便本功能不影响 agent 侧流程。

## Implementation Decisions

### 构建器修复与 cache 模块接入（前置）

- 修复单文件构建器的 shebang 剥离正则：当前正则在 CRLF 源文件上失配，shebang 被注入工厂体，产物语法错误。这是现有 6 项 viewer 测试失败的根因，必须先修。
- cache 核心模块加入构建模块序列。它是目前唯一从记忆库核心导入类型常量的模块，构建器需支持这类跨项目模块导入：在工厂体内改写为从已实例化的 store 依赖取值，入口接线时传入。
- 重建产物并更新 manifest 哈希；产物入库是预期变更。

### server：快照与三条新路由

- 快照新增 cache 节：读 cache → 过滤 pending → 复用既有读时失效派生（用快照已解析的记忆库模型算版本对照）→ 按既有分组规则分组；每组附目标记录现状（存在性、当前版本、当前正文）。cache 文件缺失视为空，不报诊断。
- `POST /api/cache/<event_id>/apply`：安检（Bearer、Origin 同源、JSON、限长、未知字段拒绝）与记录 PATCH 完全同构。锁序 cache.lock → memory.lock → evidence.lock，全部非阻塞，忙即 503。守卫链与 CLI 落库一致：非 pending 拒绝（409）、失效拒绝直写（409）、正文（提交的改写版或条目内暂存版）过单行契约（400）、store_revision 陈旧（409）。写入按操作类型复刻 CLI 落库语义：新增用 store 游标生成新 id；修订定位目标记录并重置评分投影；删除移除记录；调分先追加账本事件（幂等键 `cache-apply-<event_id>`，与 CLI 同键）再写库。全量校验、重 parse 校验、备份、原子替换后才把条目标为已处理；任何失败先于持久化返回，条目保持 pending。响应带刷新后的完整快照。
- `POST /api/cache/<event_id>/discard`：仅 pending → discarded（已落库条目拒绝，409）；只写 cache.jsonl，持 cache.lock；响应带新 cache 节。
- `POST /api/cache/prune`：语义同 CLI prune——清已处理（落库/已丢弃/读时失效）条目，支持可选天数阈值（按已处理时刻起算）；响应带 removed 计数与新快照。
- cache-only 变更不改 `store_revision` 口径；记录写入仍用「请求携带的 store_revision 必须等于当前值」的乐观并发。
- 所有新路由沿用 Host 白名单、令牌必检、错误 JSON 结构与既有状态码语义。

### 页面：暂存区面板

- 工具栏新增「暂存区」切换按钮，徽标显示 pending 计数（取自快照 cache 节）。
- 面板按组渲染：类型徽标、目标 refid、正文（修订类给原/新对照）、证据字段、失效标记与原基准对照。全部经 `textContent` 渲染，沿用现有防注入模式；窄屏全屏（沿用编辑器既有响应式处理）。
- 操作映射：新增/修订候选的正文预填暂存内容、可编辑，写入即 apply（改写版正文随请求提交）；修订类无「原样直写」快捷语义（编辑框预填即原样，改完即改写版），保持与 `-c` 等效；删除/调分候选写入前弹确认；失效组只给「丢弃」，写入入口不提供。
- 每次操作成功后用响应快照整体刷新页面状态（沿用现有 acceptSnapshot 路径）；失败时保留面板状态并展示错误，风格与编辑器冲突/锁忙提示一致。

### 文档同步（AGENTS.md 清单）

- viewer 契约参考：HTTP 表补三条路由；写入管线与并发限制段补 cache 锁序、失效/契约守卫。
- SKILL.md 紧凑查看器段与 skill README 各补一句「暂存区可在查看器中查看、编辑并入、丢弃、清理」。
- 根 README viewer 小节补一句；marketplace 的 PSM 描述补「查看器管理暂存区」，版本号递增一个次版本号。

## Testing Decisions

- 好测试只验证外部行为：通过部署产物（真实构建的 view-memoery.js）+ HTTP 断言状态码、JSON 结构与磁盘文件内容，不断言内部函数。
- 沿用既有 seam：`tests/viewer-server.test.mjs` 的黑盒形态（临时项目 + init 部署产物 + spawn 产物 + fetch API）。CLI 行为已有 `tests/memory-cache.test.mjs` 覆盖，本规格不新增 CLI 用例。
- 新增用例至少覆盖：快照 cache 节（分组与失效标记）；apply 新增落库且条目转已处理；apply 修订带改写正文、多行正文 400；失效候选 apply 409 且条目保持 pending；discard 状态机（pending 可、已落库拒）；调分候选 apply 产生账本事件且评分投影更新；新路由无令牌 401、跨 Origin 403、锁忙 503；prune 清已处理留 pending。
- 每个新增/修改用例前附中文 GWT 注释（Given/When/Then/防回归），遵循本仓库测试规范。
- 既有 6 项 viewer 失败用例随构建器修复转绿，是本规格的验收点之一。

## Out of Scope

- 查看/编辑 `evidence.jsonl` 账本。
- 在查看器里新建 cache 候选（暂存仍只走 `-a` 与收尾自动暂存）。
- CLI 行为与 `cache.jsonl` 格式的任何变更（版本号不变）。
- `store_revision` 口径变更、cache TTL/自动过期。
- 合并同类候选、批量 apply 等策展增强。

## Further Notes

- 本规格基于现场只读复核：构建器 shebang 正则缺陷、cache 模块的跨项目导入、CLI 落库/丢弃/清理语义、查看器安检链与写入管线均已逐一核实到源码行级。
- psm-cache 规格的遗留项「查看器是否展示 cache」由本规格正式关闭：倾向「首版只读不碰」被用户决定取代。
- 修复构建器后，`viewer-dist/` 产物与源码的确定性一致关系恢复，`--check` 重新可用作漂移防线。
