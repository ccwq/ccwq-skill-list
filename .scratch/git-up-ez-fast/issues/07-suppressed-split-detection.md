# ez-fast 下如何判别并声明 suppressed_split

Status: open
Type: grilling
Parent: ../map.md
Blocked by: none

## Question

ez-fast 的结果要报告「哪些路径本可按语义目的拆分，但因 ez-fast 按文件整体提交」。这个判断只有规划阶段的 Agent 做得到。判据是什么？误报与漏报的成本如何？值得为它增加一次额外的工具调用吗？

## 候选判据

1. **不填**。ez-fast 计划不带 `suppressed_split`，结果里该字段为空数组。成本最低，但用户看不到任何代价提示。
2. **Agent 读 diff 时顺带判断**。Agent 本来就要读单个文件的 diff 才能写 commit message。读到「依赖 + 脚本」混在一起时顺手记一笔。不增加工具调用，但判据不稳定，且会把规划时间重新拉回语义分析 —— 这与 ez-fast 省时间的目的相抵。
3. **只对结构化文件判别**。仅当改动落在 JSON/YAML/TOML 文件时检查是否含多个顶层键。判据确定、误报低，但漏掉代码文件里混了多个语义目的的情况。
4. **增加一次工具调用**。执行器或检查器判断某个文件是否可拆分。问题：执行器事后无法做语义判断，只能靠结构启发式。

## 权衡

- ez-fast 的核心价值是省掉语义归类。若判别 suppressed_split 本身需要同等强度的语义分析，这个字段就抵消了 ez-fast 的收益。
- 但完全不报告，用户会以为 `-z` 在任何情况下都没有代价。
- 折中方向：判据只覆盖成本极低、误报极低的情形（例如结构化文件的多个顶层键），其余留空；SKILL.md 明确「本字段是尽力而为，允许为空」。

## 需要定的

- 采用哪种判据，或明确「允许为空且不做判别」。
- 判据若落地，写在哪一层：Agent 侧（写进计划）还是脚本侧（启发式检查）。
- 漏报是否可接受 —— 用户需要知道「这个提示不保证完整」。

## 备注

该工单无阻塞，可独立推进。未决前 ez-fast 本身可用，`suppressed_split` 允许为空。
