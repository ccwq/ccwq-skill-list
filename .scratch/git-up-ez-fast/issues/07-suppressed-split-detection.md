# ez-fast 下如何判别并声明 suppressed_split

Status: resolved
Type: grilling
Parent: ../map.md
Blocked by: none

## Question

ez-fast 的结果要报告「哪些路径本可按语义目的拆分，但因 ez-fast 按文件整体提交」。这个判断只有规划阶段的 Agent 做得到。判据是什么？误报与漏报的成本如何？值得为它增加一次额外的工具调用吗？

## 候选判据

1. **不填**。ez-fast 计划不带 `suppressed_split`，结果里该字段为空数组。成本最低，但用户看不到任何代价提示。
2. **Agent 读 diff 时顺带判断**。Agent 本来就要读单个文件的 diff 才能写 commit message。读到「依赖 + 脚本」混在一起时顺手记一笔。不增加工具调用，但判据不稳定，且会把规划时间重新拉回语义分析 —— 这与 ez-fast 省时间的目的相抵。
3. **只对结构化文件判别**。仅当改动落在 JSON/YAML/TOML 文件时检查是否含多个顶层键。判据确定、误报低，但漏掉代码文件里混了多个语义目的的情况。
4. **增加一次工具调用**。执行器或检查器判断某个文件是否可拆分。问题：执行器事后无法做语义判断，只能靠结构启发式。

## 决议

采用候选 3 的精确化版本：**结构化文件增删整块启发式**，Agent 侧判定，脚本侧只做归属校验。

### 判定主体与时机

Agent 在规划阶段顺带判定，不增加工具调用 —— 读 diff 写 commit message 时顺手完成。不做全量语义分析，与 ez-fast 省时间的目的不冲突。

### 判定规则

- 仅对结构化文件：`.json` / `.yaml` / `.yml` / `.toml`。
- 仅当 diff **新增或删除了 ≥2 个不同顶层键的整块**时，把该文件标记进 `suppressed_split`。
- 纯值修改不触发：版本号联动、批量改字段名等值级修改不算「本可拆分」。
- 排除生成物：`package-lock.json`、`yarn.lock`、`pnpm-lock.yaml`、`npm-shrinkwrap.json`、`*.min.*`。理由：lock 文件天然包含成千上万顶层键但语义永远单一（依赖安装），不排除则每次全量误报。

### 强制层级（Agent 硬规则 + 软字段）

- **Agent 侧硬规则**：SKILL.md 的 ez-fast 章节写明 —— 规划时必须对每个待提交的结构化文件（按上述清单与排除项）执行增删整块判定，命中即写入该步骤的 `suppressed_split`。
- **字段本身软**：`suppressed_split` 允许为空。无结构化文件时为空是正常态；文档措辞统一为「尽力而为，不保证完整」。
- **脚本侧只校验归属，不校验判定本身**：`suppressed_split` 里的路径必须出现在该步骤的 `files` 中，否则整份计划返回 `invalid_plan`，拒绝发生在任何 Git 写操作之前（不触碰 index）。脚本不实现启发式判定 —— 与「脚本不做事后语义判断」的既有边界一致。

### 误报与漏报

- 误报：仅「改了两个不相干键的值」这类真混合不被标记（属漏报）；值修改判定规则本身不产生误报。
- 漏报：代码文件混多个语义目的、单顶层键整块混改不提示。可接受，由「尽力而为」措辞覆盖。
- SKILL.md 明确：本字段不保证完整，用户不应依赖它发现所有被抑制的拆分。

## Evidence

- 用户逐项确认（2026-10-31）：判据选结构化文件启发式；判定规则选「只算增删整块」；排除 lock/生成物；路径校验选「校验，错则拒绝」（回填工单 08）；强制层级选「Agent 硬规则 + 软字段」。
- 候选 2（Agent 全量顺带判断）被否决：判据不稳定、不可测试，且把语义分析拉回规划。
- 候选 4（脚本侧启发式）被否决：脚本复杂化（三种解析器），且与「脚本不做事后语义判断」边界擦边。

## 对下游工单的回填

### 工单 08（脚本改动面与测试口径）

- 「`suppressed_split` 里的路径必须出现在该步骤的 `files` 中，否则 `invalid_plan`（待定）」→ 已定：**是**，且校验发生在任何 Git 写操作之前。
- 新增回归用例：结构化文件增删 2 顶层键 → 标记进 `suppressed_split`；纯值修改 → 不标记；lock 文件改动 → 不标记；路径不属于该步骤 `files` → `invalid_plan` 且 index 未被触碰。

### 工单 09（文档同步面）

- 「本字段是尽力而为，允许为空」需写入：SKILL.md 的 ez-fast 章节、根 README 的 git-up 参数速查。

## 权衡

- ez-fast 的核心价值是省掉语义归类。若判别 suppressed_split 本身需要同等强度的语义分析，这个字段就抵消了 ez-fast 的收益。
- 但完全不报告，用户会以为 `-z` 在任何情况下都没有代价。
- 折中方向：判据只覆盖成本极低、误报极低的情形（例如结构化文件的多个顶层键），其余留空；SKILL.md 明确「本字段是尽力而为，允许为空」。

## 需要定的

- 采用哪种判据，或明确「允许为空且不做判别」。
- 判据若落地，写在哪一层：Agent 侧（写进计划）还是脚本侧（启发式检查）。
- 漏报是否可接受 —— 用户需要知道「这个提示不保证完整」。

## 备注

该工单无阻塞，可独立推进。未决前 ez-fast 本身可用，`suppressed_split` 允许为空。
