# ez-fast 的参数语法与组合矩阵

Status: resolved
Type: grilling
Parent: ../map.md
Blocked by: none

## Question

新增的 ez-fast 模式用什么参数表示？单独使用时的行为是什么？它能与哪些模式组合，与哪些模式互斥？

## Answer

### 参数名

`-z` / `--ez-fast`。两者完全等价，与仓库其它参数一致（`--plan/-p`、`--push/-P`、`--sub-agent/-s`）。长参数是权威名称，短参数是它的简写。

### 单独使用

`-z` 等价 `-p`：只输出可审阅的 YAML 计划，不提交，回显完整 YAML。

理由：默认模式（无参数）只生成一条 commit message，不规划不提交，拆分粒度在其中不出现，`-z` 无实际作用。而 `-p` 是产出完整计划的模式，`-z` 的全部价值都体现在「计划怎么拆」上。

### 组合矩阵

| 组合 | 结果 |
| --- | --- |
| `-z` | 等价 `-p`，回显完整 YAML，不提交 |
| `-zp` / `-pz` | 等价 `-zp`，回显完整 YAML，不提交 |
| `-zc` | 执行本会话计划，不回显 YAML，只给 JSON 摘要 |
| `-zpc` | 规划并提交。快车道与 ez-fast 同时生效 |
| `-zs` | 委派一个子 Agent 执行 `-pc`。父 Agent 在委派描述里写明 `-z` |
| `-zd` / `-z --modify` | 拒绝。`-d`/`--modify` 的用途是围绕语义边界逐问讨论，ez-fast 计划下没有可讨论的语义边界 |
| `-zi` | 拒绝。`-i` 与提交无关，与 `-s` 现有「不得与其他主模式混用」约束一致 |
| `-zP` / `-z -P` | 允许。push 契约不变 |
| `-zl zh` / `-zl en` | 允许。语言参数与拆分粒度正交 |

参数顺序无关。`-zp` 与 `-pz` 等价。

### 理由

- 拒绝 `-d`/`--modify` 是因为这两者问的是「这个改动属于哪个语义目的」。ez-fast 已经回答了「不按语义目的拆」，讨论没有对象。
- 允许 `-s` 是因为委派的是整个 `-pc` 流程，子 Agent 按文件拆分完全合理。限制它没有收益。`-z` 的传递方式走既有机制：父 Agent 在委派描述文字里写明 `-z`，描述文字本来就是硬提交边界。
- `-P` 与 `-l` 是修饰参数，与主模式不冲突，行为不变。

### 对实现的影响

- SKILL.md 的 argument-hint 要加入 `-z` / `--ez-fast`。
- SKILL.md 的模式表要新增一行，并说明单独使用等价 `-p`。
- 拒绝组合由 SKILL.md 的规则描述约束。脚本层不校验模式组合 —— 脚本只收到计划，没有模式组合信息。
- 委派时父 Agent 的描述模板要加「使用 `-z`」这一项。

## Evidence

- 仓库现有参数命名：根 `README.md` 的 git-up 参数速查表列出 `-p`/`-d`/`-c`/`-P`/`-s`/`-i`/`-l`，长名分别为 `--plan`/`--discuss`/`--modify`/`--commit`/`--push`/`--sub-agent`/`--ignore`/`--lang`。
- `-s` 的现有约束：`skills/git-up/SKILL.md` 第 97 行写明「父 Agent 只创建一个子 Agent 并等待；自然语言约束是硬提交边界」。
- 本轮用户逐项确认：单独 `-z` 等价 `-p`；允许 `-p`/`-c`/`-pc`/`-s`；拒绝 `-d`/`--modify`/`-i`；`-P`/`-l` 照常；`-z` 与 `-s` 组合时父 Agent 在描述里写明 `-z`。
